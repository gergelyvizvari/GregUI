# Component development candidates

Source review: 28 October 2026. Open candidates are proposals, not implemented APIs or an approved delivery plan. The DataTable, Combobox and ConfirmDialog first increments were delivered on 28 October 2026; see the expanded contracts and verification record. Priorities reflect reuse and gaps visible in this repository; no external consumer-demand study was performed.

## Postcard-driven shared foundations — 29 October 2026

Owner-selected addition: VisualChoiceGroup and DocumentPreview, composed in a local Postcard studio playground example. The first increment supplies controlled visual single selection, disabled/status feedback, fixed document dimensions, controlled page switching, fit/zoom and optional safe-area guides. These are reusable presentation APIs; postcard templates, personalisation, address storage, AI generation and print/PDF export remain consumer responsibilities. See component contracts and VERIFICATION.md for executed checks and limits. This takes priority over the previously suggested FileUpload extension; authentication remains deferred.

The follow-up AddressFields increment adds controlled address entry with configurable country/field policy and per-field feedback. Postcard studio now defaults to Hungary with Hungarian/UK entry and preview policies, basic postcode checks and domestic/cross-border country lines; provider lookup, address verification and storage remain consumer work.

The next delivered composition adds flat/folded card selection, cover/open-inside/back previews and separate envelope recipient drafts. DocumentSpread provides the reusable two-panel layout; duplex imposition and print/PDF output remain future application work.

## Previous focus — typography and page foundations

Owner-selected priority: a shared foundation for all app types. First increment delivered: shared typography roles, h1–h6, lead/caption text, Prose reading flow, a reading-width container and compact page-header breadcrumbs/metadata with nested section levels. ## Cross-cutting findings

- Documentation had drifted: README listed existing inputs as future work, palette totals omitted Iris/Lagoon, and some prose still described five styles. The AI guide and corrected overview now distinguish shipped behaviour from proposals. Historical verification entries remain historical evidence.
- `ThemeSelector` uses the literal suffix `(saved)` and token-owned English style/palette names. A later localisation pass could expose translations while retaining stable stored IDs. Combobox now uses the provider locale for case folding. TreeView still uses the runtime default locale; test its intended matching behaviour before changing it.
- Data/input modules import shared primitives through `index.tsx`, which re-exports those modules. This creates barrel cycles. The current checks can pass with this structure; it is a maintenance concern, not a demonstrated runtime defect. Consider internal primitive modules when touching these areas, without changing public imports.
- `index.tsx` and `styles.css` contain many component families. Keep public exports stable; split internal modules only where it makes an actual feature change easier to maintain. Avoid coupling a large structural rewrite to the first feature increment.

## Definition of a completed increment

Preserve existing default behaviour; document controlled/uncontrolled state and consumer responsibilities. Add public-export workbench usage and meaningful regression checks. Keep styling inside shared packages and package-owned feedback translatable. Verify affected light/dark, portal, RTL, narrow-screen and keyboard states, then record actual results and untested gaps in VERIFICATION.md. The current support policy is a target, not proof that every proposed interaction has been verified.

Charts, rich-text editing, drag-and-drop trees and custom calendar surfaces should wait for a concrete consumer workflow. Their scope and accessibility requirements are substantially larger than extending the existing foundations.
